# 映射程序 → 硬件队友：电机目标接口 v1

## 1. 五根杆的物理位置

| 杆标识 `rod` | 皮影上的连接位置 | 摄像头模式的输入来源 |
|---|---|---|
| `wusong_neck` | 武松脖子处的主杆 | 双肩中点，作为颈部位置的近似 |
| `wusong_left` | 武松左手 | 人体左腕相对左肩的位置 |
| `wusong_right` | 武松右手 | 人体右腕相对右肩的位置 |
| `tiger_head` | 老虎头部，杆固定在耳朵处 | 摄像头模式不从人体头点驱动，保持标定中位 |
| `tiger_tail` | 老虎尾巴处 | 摄像头模式保持标定中位 |

左右指角色自身的左右。视觉 Pose9 没有单独的脖子关键点，双肩中点是本项目采用的近似；它不是检测模型直接输出的颈部点。老虎的 `tiger_head` 名称描述被控制的头部，实际固定点是耳朵处。剧本模式能编排全部五根杆。

五根杆不等于五个电机，也不意味着必须十个电机。每根杆有几个实际可控轴，由机械结构和硬件轴表决定。模拟配置不能直接代替实物标定。

## 2. 首选对接位置：同一 C++ 程序里的 MotorBackend

```text
视觉 Python → 输入适配/消息 → C++ 姿态映射
→ 五根杆的目标 → 各轴标定、角度限制、平滑、速度限制
→ ControlTick.axes 中的 angle_deg
→ 硬件队友实现的 MotorBackend::send(tick)
→ 实际驱动接口 → PL/PWM → 电机与皮影
```

接口在 `include/shadow/motor_backend.hpp`：

```cpp
class MotorBackend {
public:
    virtual ~MotorBackend() = default;
    virtual void send(const ControlTick& tick) = 0;
    virtual void shutdown() = 0;
};
```

硬件队友在 `send()` 中接收同一控制周期的全部轴，按 `axis_id` 找到真实电机通道，只把 **`axis.angle_deg`** 当作本周期电机目标。

`limited_target_deg` 是经过角度限位、尚未经过完整平滑和速度限制的诊断值，不能代替 `angle_deg` 发给电机。`input_state` 和三个限制标记都是诊断字段。程序输出的是角度命令，不是已经测得的电机位置；是否有位置反馈由硬件确定。

## 3. 可选 JSONL 格式

新增 `JsonlMotorBackend` 便于对照、记录和定义独立软件边界；默认 CSV 轨迹仍可用于原有 SVG 预览。

```bash
./build-linux/shadow_show --seconds 1 --motor-format jsonl > build-linux/motor_targets.jsonl
```

上述命令只导出数据。JSONL 后端不会访问电机、寄存器或 AXI，也没有新增板端硬件接收进程。真正驱动电机时，优先由硬件队友实现同进程 `MotorBackend`。如果双方另行选择独立进程传输，仍须实现并约定传输方式、连接生命周期、超时和接收端校验。

一行一个完整 JSON 对象，一行包含一个控制周期的全部已配置轴。下例只演示一个轴的结构；实际输出 `axes` 包含当前配置的所有轴：

```json
{"version":1,"type":"motor_targets","seq":1,"time_s":0.02,"mode":"camera","paused":false,"playback_s":0.0,"axes":[{"axis_id":"neck_pan","rod":"wusong_neck","angle_deg":90.0,"input_state":"tracking_or_holding","input_clamped":false,"angle_limited":false,"speed_limited":false}]}
```

### 顶层字段

| 字段 | 类型与含义 |
|---|---|
| `version` | 整数，固定为 `1` |
| `type` | 字符串，固定为 `motor_targets` |
| `seq` | 无符号 64 位整数；每个 JSONL 后端实例从 `1` 开始，每成功写出并刷新一帧增加一次 |
| `time_s` | 有限、非负数；程序控制时钟，单位秒。不是摄像头曝光时间，也不是 UTC 时间 |
| `mode` | `stopped`、`script`、`touch`、`camera` |
| `paused` | 布尔值；暂停剧本时保留 `mode: "script"`，此字段为 `true` |
| `playback_s` | 有限、非负数；当前剧本播放进度，单位秒，不用于硬件超时判断 |
| `axes` | 非空数组；一个周期的轴目标，轴数由标定配置决定 |

### 每轴字段

| 字段 | 类型与含义 |
|---|---|
| `axis_id` | 非空字符串，仅字母、数字、下划线、连字符；同帧唯一，用于查硬件通道 |
| `rod` | 上表的五种杆标识之一 |
| `angle_deg` | 有限数，单位度；经过全部软件限制后的电机目标命令 |
| `input_state` | `no_input`、`tracking_or_holding`、`returning_to_neutral`、`command_held` |
| `input_clamped` | 杆目标坐标发生过软件截断，仅诊断 |
| `angle_limited` | 角度目标被软件限位，仅诊断 |
| `speed_limited` | 本周期命令受速度限制，仅诊断 |

后端先验证并序列化整个 `ControlTick`，任何轴的 ID、杆枚举、角度或诊断枚举不合法，都在写出前拒绝该帧；空轴数组、非法模式、无穷大或 NaN 时间也拒绝。成功后追加换行并立即 `flush()`。轴数组保留配置顺序，但接收端应按 `axis_id` 对应，不应猜测数组下标就是 PWM 通道。

序列号是输出端自己的计数，与视觉输入的 `seq` 无关。输出后端重建会从 `1` 开始；如果用 JSONL 做跨进程连接，每次连接必须显式重新初始化接收状态，不应让新进程直接续接旧会话。序列号溢出报错，不回绕。

写入或刷新失败会抛出异常；底层 I/O 故障可能产生不完整的一行，所以外部接收端只能在读到完整换行、解析并验证整个对象后接受它。逐行刷新不提供 PL 同步提交，也不提供文件断电持久化保证。

## 4. 硬件队友必须补齐的部分

### 4.1 一张真实轴表

每个实际电机轴都填写以下信息，并使程序标定配置与硬件后端一致：

| 项目 | 用途 |
|---|---|
| `axis_id`、所属 `rod`、实际运动方向 | 软件轴到实物轴的一一对应 |
| 电机型号、驱动通道、是否有反馈 | 确定输出和初始化方式 |
| 中位角、最小角、最大角、最大速度 | 实物标定和机械行程约束 |
| 角度到 PWM/其他驱动量的标定关系 | 驱动端转换；不能假设所有电机都使用同一脉宽范围 |
| PWM 周期、脉宽/计数单位、计数时钟 | 仅在实际驱动为 PWM 时填写 |
| 实际接口、寄存器布局或驱动 API | 确定 C++ 如何访问硬件 |

一个杆含有两个轴时，应有两个不同的 `axis_id`，共享同一 `rod`。同杆目标如何影响各轴由标定或后续机械模型决定。当前线性映射是初版模型，必须结合实物方向和行程校准。

### 4.2 角度输出与整组更新

硬件后端按标定把 `angle_deg` 转成驱动量，再通过真实驱动或寄存器输出。若 PL 提供多轴暂存寄存器和统一提交信号，应先写完所有轴，再统一提交，避免同一组新旧目标混杂。

现有材料没有确定电机 IP 的地址、寄存器偏移、计数单位或统一提交机制，本程序没有编造这些参数。若硬件只支持逐轴更新，需要由硬件队友说明其时序并确认是否满足协调动作要求。

硬件接收端应校验本次配置预期的完整轴集合、重复/未知轴和自身限制后再更新；导出器只验证单帧结构，无法知道某个外部硬件预期有哪些轴。

### 4.3 初始化、超时与停止语义

- 启动时，由硬件后端先完成初始化/回零或建立已知命令状态，再将对应初始角交给映射器。软件中的初始角不是自动测得的物理位置。
- 视觉短暂丢点的保持/回中由映射层处理；程序卡死或退出后无法继续执行这一逻辑。硬件侧仍需要独立看门狗和明确的失联动作。
- 看门狗使用硬件接收时刻或实际硬件计时器，不能依赖发送方 `time_s` 自报时间。
- `mode: "stopped"` 表示演出控制器正在按软件规则回中，不等于电机断电或急停。`paused: true` 表示继续保持本周期命令。
- 真实 `shutdown()`、使能、急停、失联后保持/回中/去使能策略由硬件队友结合电机和机械确定。现有 CSV/JSONL 的 `shutdown()` 仅刷新输出。
- CSV/JSONL 导出可用于 PC 联调；它们不构成已完成的硬件驱动或上板验证。

## 5. 三人的交付边界

- **视觉队友**：在最新 FOLLOW 最终 `pose` 处接入输入适配，输出约定的有效关键点消息；提供实测数据与丢人/换人示例。触控屏按约定发送杆或关键点输入。
- **你**：交付 C++ 映射与控制程序、输入适配约定、脚本/音频/标定配置，以及以上 `MotorBackend` 和电机目标格式。
- **硬件队友**：填写实物轴表，实现真实 `MotorBackend`、驱动/PWM/PL、初始化及看门狗，完成 PetaLinux/ARM64 集成和上板调试。
