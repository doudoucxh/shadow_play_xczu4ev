# MPSoC-P4 板端接入说明

## 已知项目基线

来源：项目已有 `handoff_visual_follow_20260922/交接说明.md`。

- 正点原子 MPSoC-P4／XCZU4EV；Vivado／Vitis 2022.2，板端 Linux。
- 现有相机／DPU／HDMI 使用专用 PL DMA／显示流水线。
- 原视觉运行入口为 FOLLOW，DPU 模型为 Pose9，输入相机画面 1280×720。
- 这些是项目交接记录，**不是本次重新登录板端确认的软件清单**。
- 本 UI 的 1024×600 是界面视口，与相机的 1280×720 输入尺寸不是一回事。

## A. Linux 桌面能输出到该 HDMI

需要板端已有可用的 DRM／显示驱动及 X11 或 Wayland 图形会话，且该会话真正显示在外接屏幕上。
ARM64 Chromium 与 Python 必须匹配板端系统的架构、glibc、动态库和图形栈；不能把电脑的 x86 Chromium 直接复制过去。

在桌面设置里使用屏幕实际支持的显示模式；若 EDID／驱动没有 1024×600，需要硬件组配置像素时钟、VTC／HDMI 时序或驱动模式。
网页的 window-size 参数不能生成板上缺失的硬件时序。
本脚本不会执行 xrandr 改模式、写 /dev/mem、重配 DMA 或更新设备树。

确认桌面和触摸正常后，运行 `sh runtime/start-linux.sh`。
UI 固定最大宽度 1024、比例 128:75；在更大桌面会居中，不拉伸皮影。
系统和浏览器缩放均设为 100%，触摸输入应映射到实际 HDMI 屏幕。

## B. 仍只有原 PL／VDMA 的摄像头显示系统

这种环境中，网页文件和 HTTP 端口不会自动变成 HDMI 像素。
队友需要选择并实现一条真正的渲染路径：

1. 在 Linux 系统镜像中集成能驱动该 HDMI 的图形输出栈、ARM64 Chromium 和输入支持，再使用 A；或
2. 用 Qt WebEngine／浏览器渲染引擎生成界面帧，再接入项目现有的显示对象 `display.present(frame)`，并把触摸事件送回渲染引擎。

第二条不是现成接通的脚本。本包不猜测物理帧缓冲地址、不直接写 VDMA 寄存器，也不会把截图循环冒充流畅的交互界面。
对应源码位置可参考项目原 `follow/display_queue.py` 和 `base_runtime/runtime.py`；需要队友在实际板端确认：

- 显示对象接受的分辨率、stride、像素格式和缓存同步方式；
- 1024×600 与现有 HDMI 输出时序之间的匹配或缩放方式；
- 双／三缓冲交接和显示所有权，避免现有视频服务与 UI 同时控制同一输出；
- 触摸事件坐标、页面点击／画板拖动，以及停止后的原视频恢复。

记录中 `VdmaFullFrame` 固定 `W=1280,H=720`，`present(frame)` 把 NumPy `uint8` 的三通道 BGR 帧复制到显示缓冲。
因此不能把 1024×600 网页帧直接交给这个旧实现。若保留 720p 时序，应由渲染适配层等比缩放并补边到 1280×720，
触摸坐标也要反向映射；若要求物理输出就是 1024×600，则须同步核对 PL 时序、显示驱动及缓冲大小，不能只改 Python 的宽高。
旧 `DisplayQueue` 仅保留最新一帧（队列容量 1），并拒绝超过 250ms 的过期帧；桥接时应保留这种防积压方式。

这些硬件运行文件未混入本 UI 启动目录，避免队友误启动另一个摄像头／HDMI 驱动入口。
原服务如何停用、如何回退，应按队友当前采用的板端版本执行，不能照搬历史临时服务名。

## 摄像头和人体关键点

浏览器 getUserMedia 需要安全上下文。板端本机 `http://127.0.0.1:8765/` 可请求摄像头；
从别的设备用板子 IP 的普通 HTTP 打开，只能作为界面查看，不应据此判断摄像头故障。
USB 相机需要 V4L2／浏览器支持；PL DMA 相机需额外接成浏览器可用视频源。

页面已提供 JavaScript 接口，**只画真实传入的结果**：

```js
window.ShadowCameraFeed.updatePose({
  head: [0.50, 0.18],
  leftShoulder: [0.35, 0.32], rightShoulder: [0.65, 0.32],
  leftElbow: [0.25, 0.45], rightElbow: [0.75, 0.45],
  leftWrist: [0.20, 0.65], rightWrist: [0.80, 0.65]
});
```

以上数字只是接口格式示例，不是实际识别结果；不要作为设备演示中的假检测结果。
接口在“以身入戏”且摄像头已开启时生效。坐标是正向视频画面的归一化值，原点左上，x 向右、y 向下。
FOLLOW Pose9 的像素坐标应除以实际图像宽高；原链路已旋转 180°，不要再次旋转。
无效点不要传入，无有效头／双手腕时应发送空结果以清除覆盖层。连续 1.2 秒没有新结果也会清除旧标记。
像素数据不在 updateFrame 中传输；updateFrame 只接受尺寸与可选 pose 元数据。
外部进程到 JavaScript 的传输桥接需要队友接入，本包没有把 Python DPU 进程与浏览器自动连接。

## 交接验收

1. 断网仍可打开首页，初始菜单隐藏，点击能显示／收起三入口。
2. 三个页面均可进入和返回，合书后首页画面不再二次跳变。
3. 图像、旗帜和字体齐全，1024×600 下没有浏览器边框、缩放或控件遮挡。
4. 触摸画板能连续画线；识别后左侧使用标准皮影姿势，展臂双手等高。
5. 存入至少三个动作，播放、暂停、删除可用；重启浏览器后序列仍在，启动回到首页。
6. 相机确实显示实际画面；接入 DPU 后，仅有效真实关键点进入覆盖层。
7. 如需电机／丝杆联动，另行核对控制侧接口和限位；本包没有发送硬件控制指令。
8. 手动通过后再配置自启动，并记录断电重启后的 HDMI、触摸及退出恢复结果。
